# ARCHITECTURAL DECISION RECORDS (ADR)

## ADR 001: Offline Mock Repository Architecture
- **Status:** Approved
- **Context:** Local LLM agents need predictable, fast test environments without spinning up external database containers or live backend APIs.
- **Decision:** Implement all data access interfaces under `src/repositories/` backed by stateful in-memory implementations in `src/repositories/mock/`.
- **Consequences:** All features can be completely built, rendered, and validated (`npm run build`, `npm test`) purely in offline front-end space.

## ADR 002: Sequential Worker Execution Rule
- **Status:** Superseded (2026-08-20) — project no longer runs on local Ollama; the VRAM constraint that motivated this ADR no longer exists.
- **Context (historical):** Spawning multiple concurrent worker agents risked exhausting GPU VRAM and stalling local Ollama models.
- **Decision (historical):** The Queen Bee invoked worker bees sequentially in single passes.
- **Superseding decision:** The Queen Bee may dispatch worker bees in parallel when their task scopes don't overlap (e.g. different `src/features/*/` directories) and don't have a dependency ordering (e.g. a feature bee depends on Architect Bee's foundation landing first). Bees whose file scopes could conflict, or where one bee's output is another's input, are still sequenced.

## ADR 003: Consolidation-Readiness Audit (§87, Phase 12 "Advanced Accounting")
- **Status:** Approved — audit only, no code changes made as a result of it.
- **Context:** SA_ACCOUNTING_MASTER_SPEC.md §87 does not ask this project to BUILD consolidated financial statements — it asks to "architect for future support" of parent companies, subsidiaries, intercompany transactions, elimination entries, non-controlling interests, consolidation adjustments, and consolidated financial statements, and explicitly warns: "Do not design the database in a way that makes consolidation impossible later." This ADR records a real audit of the current schema against that bar (2026-08-22), not a guess.
- **Finding — nothing in the current design blocks consolidation, but nothing enables it yet either:**
  - **No domain entity carries a `companyId`.** `Company` (`src/types/company.ts`) exists as a real, standalone entity, but `Customer`/`Invoice`/`JournalEntry`/`Account`/every other domain type does not reference it — already flagged in `docs/SA_SPEC_GAP_ANALYSIS.md`'s Phase 1 section as the pre-existing "multi-company tenant scoping" gap (§75). This is the SAME missing piece §87 needs first: consolidation cannot exist before multi-company data does. It is a large, additive, separate migration (tag every domain type with a `companyId`, add access-control scoping) — not attempted here, and not blocked by anything in today's schema (every field addition needed is optional/additive, the same "backward-compatible field addition" pattern already used repeatedly in this codebase, e.g. `DocumentLineItem.warehouseId?`, `JournalEntry.currency?`).
  - **`Account.subType` is a free-form `string`** (`src/types/account.ts`), not a closed enum — a future Non-Controlling Interest equity account, or an Intercompany Receivable/Payable account type, needs zero type-system changes to add, only a new seeded `Account` row.
  - **`JournalEntryService` is deliberately the ONLY place allowed to decide whether a set of lines balances** (`docs/LEDGER_ARCHITECTURE.md`). Elimination entries and consolidation adjustments are NOT real transactions of any single company — they must never be posted into a real company's own `JournalEntry` ledger (that would corrupt that company's own standalone GL and audit trail). The correct future design is a SEPARATE, parallel structure (a `ConsolidationAdjustment` repository/service, scoped to a consolidation run, never touching `IJournalEntryRepository`) — the same "layer a new structure on top rather than retrofit an existing invariant" pattern this codebase already used for `StockLot` (layered on top of the append-only `StockMovement` ledger without altering it) and for the Deferred Tax / Expected Credit Loss computations (movement-only postings that never rewrite a prior posted entry). Nothing in `JournalEntryService`'s design prevents this — it would simply never be called for elimination entries.
  - **Non-controlling interest** needs an ownership percentage on the (not-yet-existing) parent-subsidiary relationship, consumed by a consolidation calculation layered on top of consolidated equity, analogous to how `calculateBalanceSheet()` already layers a "Current Year Earnings" line on top of stored account balances rather than requiring a year-end closing journal to exist first (see that function's own doc comment) — the same "compute it, don't require the underlying ledger to already reflect it" technique would apply again here.
- **Decision:** No code changes. The schema is confirmed NOT to block future consolidation. The real prerequisite work (multi-company tenant scoping, §75) is a separate, larger, deliberately-deferred migration — tracked in `docs/SA_SPEC_GAP_ANALYSIS.md`, not scheduled by this ADR. A future consolidation build should: (1) do the multi-company migration first, (2) add `Company.parentCompanyId`/ownership-percentage fields, (3) build a separate elimination/adjustment layer that never posts into any single company's own `JournalEntry`, (4) build consolidated statements as a NEW read-only report (mirroring how Income Statement/Balance Sheet/Cash Flow are already pure functions over real posted data, never a second source of truth).
